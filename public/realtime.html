Real-time with minimax/h3-max/lip-sync/image-to-video

Can I get real time on this API?

No, not in the live-streaming sense. This is a batch generation endpoint.

  • How it runs: you submit a job to fal's queue, then poll for the result or receive it on a webhook. You can submit a request, check whether it is still in progress, and fetch the result once it is done. There is no streaming or WebSocket mode for live lip-sync.
  • What you get back: a finished video file. You send an image and audio and get a lip-synced video, at resolutions from 480p to 2K, 5 to 15 seconds per request, billed per second of output. It costs from $0.05 per second.
  • Latency: fal doesn't publish a typical generation time, and the each::labs listing shows no median runtime. The video-to-video sibling returns a timing breakdown, where "inference" is the GPU denoising time summed over every window the request generated. Run a few calls at your target resolution and measure. Expect seconds to minutes per clip, not frame-by-frame speed.

If you need a talking avatar that answers live, for example on a call or in a chat widget, you need a streaming avatar product rather than this model. A middle ground is to pre-generate short clips with H3 Max and stitch them together.

Sources: fal – H3 Max Lip Sync Image to Video (API); fal – H3 Max Lip Sync overview; fal – H3 Max Lip Sync Video to Video (API).

Do I need a RunPod to run it for real time?

No. A RunPod GPU wouldn't make this model real-time, and you probably couldn't run this exact model there anyway.

  • You can't get the exact model. H3 Max is fal's own post-trained version of MiniMax H3. fal describes the base H3 as open-weight, but nothing on their pages suggests the H3 Max weights are released. On RunPod you would most likely run base H3, which is a different model.
  • The model isn't built for live use. It is a diffusion video model that generates a whole clip by repeatedly denoising it. Real-time lip-sync needs about 25–30 frames out every second, starting within a fraction of a second. On a single rented A100 or H100, a model like this takes much longer than the clip itself to render. More GPU makes each clip faster, but it doesn't turn a clip generator into a streaming one.

What RunPod would give you:

  • No fal queue wait or per-second fee, which helps at high volume.
  • Control over cold starts. You can keep a warm pod so jobs start immediately.
  • Your own concurrency and batching.

It is still batch generation, just on your own hardware.

Realistic options

  1. Truly live (avatar on a call or in a chat widget): use a streaming avatar API or a lightweight real-time lip-sync model built for live video. Some of these can be self-hosted on a RunPod GPU, and that is where RunPod actually earns its place.
  2. Near-real-time (a few seconds' delay is fine): keep H3 Max on fal and generate short chunks in parallel as the audio arrives, then play them back to back.
  3. Pre-rendered: generate clips ahead of time with H3 Max and serve them.
